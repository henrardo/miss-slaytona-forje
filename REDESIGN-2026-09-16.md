# Redesign: agents in isolation, served as a product

Written 2026-09-16, against commit `35e182e` ("second commit -- pre migrate to
isolation"). Nothing in this document has been implemented.

## The goal

A user installs a package, runs a CLI, points it at any repo on their machine,
states a goal, and talks to a swarm of agents that work on it. The agents share
a Neo4j memory graph. Each agent sees only the repo it was given.

## Probed facts, not assumptions

Every claim below was measured today. They decide the architecture.

| question | answer |
|---|---|
| Does Vibe install and import in a Daytona sandbox? | yes — `vibe 2.25.4` |
| Can a Daytona sandbox reach PyPI / GitHub / OpenAI? | yes, TLS 1.3 on 443 |
| Can a Daytona sandbox reach the served model? | **no** — TCP 443 opens, TLS handshake reset |
| Can a Daytona sandbox reach Neo4j Aura? | **no** — 443 reset, 7687 times out |
| Can that be opened per sandbox? | **no** — `domain_allow_list` → *"Network access is restricted and cannot be overridden at the sandbox level"* |
| Does `network_allow_list` help? | no — takes CIDR, and restricting to two /32s breaks DNS |
| Can the RunPod pod reach Neo4j Aura? | yes — 7687 open |
| Can the RunPod pod reach OpenAI? | yes |
| Can the RunPod pod reach Daytona's API? | yes — `app.daytona.io`, `api.daytona.io` TLS ok |
| Is the model reachable from the pod without a proxy? | yes — `localhost:30000` |
| Is docker available inside the pod? | **no**; the pod runs as uid 0 in its own container |

The block is SNI-based host filtering on Daytona's egress: TCP connects, then
the handshake is reset once the middlebox reads the hostname. openai/pypi/github
complete; our two hosts do not.

**Consequence: Daytona cannot host the agents.** It stays what it already is —
the grader, which only needs PyPI and its own API.

## Where things run

```
  operator's machine            RunPod pod                       Daytona
  ------------------            ----------                       -------
  CLI client          ──HTTP──▶ swarm server                     grader
    repo, goal,                   ├─ sglang  (localhost:30000)   pytest on an
    test command                  ├─ agent-0  own dir, own user  uploaded tree
    streamed output               ├─ agent-1  own dir, own user
    messages in                   ├─ step-memory sidecar (localhost)
                                  └─ Neo4j client ──bolt──▶ Aura
```

The repo under migration is uploaded to the pod, one copy per agent. This repo
— the harness — is never on the pod, so "the agent sees only the repo it was
asked to work on" holds by construction rather than by patching leaks.

Isolation between agents: one unix user per agent, one directory each, mode
0700. Not docker — the pod has none, and nesting containers on a GPU pod is not
worth it for this.

## What changes

### Moves to the pod
- Vibe invocation (`_run_vibe`), one per agent, cwd = that agent's repo copy
- `step_memory` sidecar — still a loopback socket, just a different loopback
- the memory MCP server, with Neo4j credentials present there
- `id_fix_proxy`, or it disappears: usage can come from sglang directly now
  that nothing needs the id-rewriting hack across a network boundary

### Becomes an input instead of a constant
- the repo (today: `seed_repo` copies `fixture/`)
- the goal (today: 52 pydantic references in `orchestrator/`)
- the dependency install step (today: `requirements-v2.txt` in three places —
  agent venv, each checkout, and the Daytona snapshot image)
- the test command (today: `python -m pytest tests -q`)

### New
- an HTTP/WS API on the pod: create run, stream entries, send a message to an
  agent, fetch the resulting diff
- a CLI client: `msf <repo> --goal "..." --test "pytest -q"`
- repo upload and diff-back. Agents work on a copy; the user applies a patch.
  Nothing writes to their working tree without them asking.

### Dies
- `seed_repo` from the bundled fixture, and the fixture itself as a product
  dependency
- `snapshot.py`'s `INCLUDED_RELATIVE_PATHS` pinned to `fastapi_mail`/`tests`
- `observed_fix`, the shim check, the gutted-validator check — all
  pydantic-specific, and there is no general replacement
- the 8-of-8 answer key, which only exists because `reference_v2` is bundled
- warm/cold as the entry point; it becomes one scripted client of the API

### Survives unchanged
- `neo4j-agent-memory` and every call the harness makes into it
- Vibe's `post_tool`/`post_agent` hooks and `--output streaming`
- `SandboxPool.run_pytest` — the grader's shape is already right
- the sweep/cleanup handlers

## What this costs

- **No result before the change compares to any after it.** Different machine,
  different latency, different tool surface.
- **Credentials live on the pod**, in each agent's environment. `_STRIPPED_ENV`
  exists to keep them out of an agent's reach; that protection is gone. A
  separate unix user per agent limits it to "the agent can reach the graph and
  the model", not "the agent can read the operator's keys".
- **The anti-gaming gates go**, and with an arbitrary repo and an arbitrary test
  command there is no way to detect a gutted suite. The user's own tests are
  the only signal.
- **Talking to agents breaks comparability** — a run someone intervened in
  cannot be compared with one they did not.
- **Most of `run.py`** (~1,250 lines) is batch orchestration shaped around the
  current arrangement and does not survive.

## Open questions, in the order they block work

1. How do N agents get isolated on one pod — unix users, or a pod per agent?
   A pod per agent is clean and costs $0.49/hr each.
2. Where does the swarm server's API terminate, and how is it authenticated?
   RunPod's HTTP proxy is public per port.
3. Does grading stay in Daytona, or move to the pod? Grading in the agent's own
   environment lets it tamper with its verdict; a second clean container on the
   pod avoids that without Daytona at all.
4. What replaces `errors_cleared` as a progress measure when there is no answer
   key and no fixed error chain?
