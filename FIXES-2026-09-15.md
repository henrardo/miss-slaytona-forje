# What was fixed — 2026-09-15

Companion to [AUDIT-2026-09-15-fix-spec.md](AUDIT-2026-09-15-fix-spec.md)
(the diagnosis). Operational knowledge lifted out of the code comments is in
[NOTES-hard-won.md](NOTES-hard-won.md).

## The result

The harness now grades attempts. That is the whole of it, and everything else
follows.

Two runs, both with the repaired loop. The 4-a-side run is the demo's own
mechanic; the 2-a-side one gives each agent a larger share of the card.

|  | before (40 runs, 63–102) | after, 2 a side (700s) | after, 4 a side (900s) |
|---|---|---|---|
| `ATTEMPT_DONE` (attempts graded) | **0** in 19 of last 20 | 9 | **26** |
| `SANDBOX_CREATED` (oracle ran) | **0** in 19 of last 20 | 9 | **26** |
| `ATTEMPT_REJECTED` (shim/gutted) | n/a, check never reached | 1 | 7 |
| `MEMORY_READ` (ever emitted) | **never, in any run** | 4 reads, 3 hits | 17 reads, **79 hits** |
| `MEMORY_WRITE` | 0 in all 40 | 2 | 0 |
| `best_passed` (tests passing) | **0** in all 40 | **2** | 0 |
| `errors_cleared` (best) | 0 in all 40 | warm 2, cold 1 | warm 1, **cold 2** |
| attempts, warm / cold | 1 each | 4 / 5 | 17 / 9 |
| `token_ratio` | noise ~1.0 | 0.825 | 0.887 |

**7 of 26 graded attempts (27%) were rejected** for shimming `pydantic.v1` or
deleting behaviour, in both arms. That is the model's dominant strategy on this
codebase, and before the loop was fixed the check had never once been reached.
Any result from a harness without those two gates is measuring a 97%-gameable
oracle.

The clearest single instance, from a later run:

```
ATTEMPT_REJECTED  cold-1 attempt 1:
    pytest_passed=31
    shimmed=[config.py, fastmail.py, schemas.py]
```

**31 of 33 tests passing, by shimming three files to `pydantic.v1`.** The suite
cannot see it; nothing else in the harness could have. Note that
`pytest_passed` reads 31 and not 0 — the gate now blocks `success` and the
progress metrics without falsifying what pytest actually said, which is the
§"Honesty of the measurement" fix below doing its job on a real attempt.

At 8 agents the card is saturated (~36s/turn), so the 4-a-side run made *less*
progress per agent than the 2-a-side one — `best_passed` 0 against 2. That is
the throughput constraint, not a memory result.

**Do not read either run as a warm-vs-cold finding.** Both predate the
prompt-order fix below, and in the 4-a-side run its effect is stark: warm took
**17 attempts at 29.9k tokens each** to cold's **9 at 50.1k**, and cold cleared
*more* errors (2 vs 1). Warm was not doing better cheaper; it was ending its
attempts after ~2 productive turns.

The demo's core mechanic is observable for the first time. From the recorded
run (`runs/golden.jsonl`):

```
t=251  ATTEMPT_REJECTED  warm-0 shimmed pydantic.v1 into config.py, fastmail.py
t=254  MEMORY_READ       warm-0 attempt 2: hits=1 sources=['warm-0']
t=435  MEMORY_READ       warm-1 attempt 2: hits=2 sources=['warm-1','warm-0']  <-- cross-agent
t=654  MEMORY_WRITE      warm-1, warm-0, on "progress"
```

`sources=['warm-1','warm-0']` at t=435 is warm-1 reading a trace warm-0 wrote
90 seconds earlier in the same run. That is the sentence the talk is built on,
and until now it had never happened.

**This is not yet a demo-ready result.** Neither arm converged in either run.
What was fixed is the instrument, not the finding: before this, the experiment
could not have detected a warm/cold difference if one existed, because warm
retrieved nothing. Now it can. See "What is still open".

## Root cause

Three independent faults had to line up, and each is individually silent — it
produces a run that completes, prints a plausible summary, and measures
nothing.

**1. One Vibe invocation consumed the whole run.** `_run_vibe` was handed the
entire remaining deadline. Vibe's loop exits only on a text-only assistant
message and the model never emitted one (measured: 22 and 19 tool-calling
turns, zero text-only). So `pool.run_pytest` was called with
`timeout=max(0.0, deadline - now)` = `0.0` and raised every time. Daytona
never ran; every trace closed "ran out of time mid-attempt";
`_reasoning_context` correctly filters those out, so **warm retrieval was
empty by construction** and warm ≡ cold. That is the entire flat
`token_ratio ≈ 1.0` series.

Fixed with Vibe's own `--max-turns` (bounds the attempt on a turn boundary, so
the transcript stays clean and resumable) plus a reserved `VERDICT_RESERVE_S`
for the oracle. An attempt that cannot afford its verdict is not started.

**2. `--max-turns` is cumulative across `--continue`.** Found while verifying
fix 1. `TurnLimitMiddleware` tests `stats.steps - 1 >= max_turns` against the
*whole session's* step count, and `--continue` restores it. Measured against
the proxy's request counter: a session with 3 users and 3 assistants resumed
with `--max-turns 2` made **0** completion requests; with `5`, **0**; with `8`
(= 6 + 2), exactly **2**.

A flat per-attempt allowance would have given attempt 2 onward zero turns —
the agent appears to run, produces nothing, and is still graded. `_steps_used()`
reconstructs the count (`users + assistants`) from the transcript.

Confirmed in production once the run emitted `turns_used`/`resumed`:

```
warm-0 att=1 turns=9  resumed=False  stop='Turn limit of 8 reached'
cold-0 att=1 turns=9  resumed=False  stop='Turn limit of 8 reached'
cold-0 att=2 turns=17 resumed=True   stop='(no stop event) vibe timed out after 254s'
warm-0 att=2 turns=16 resumed=True   stop='(no stop event) vibe timed out after 259s'
```

Attempt 1 uses its 8 turns and stops on the limit; attempt 2 resumes and adds
8 more (9 → 17) and 7 more (9 → 16). Attempt 2 ends on the wall backstop rather
than the turn limit because the run deadline was closing — which is the
backstop working, and is now *visible* rather than silent.

Also: `--max-turns` **exits 1**, so the old `resume = last_exit == 0` would
have refused to resume on every attempt, throwing away the agent's context each
time. `_ended_cleanly()` keys on Vibe's own `<vibe_stop_event>` marker instead,
while still refusing to resume a session that died of context overflow.

**3. Vibe blocks forever on inherited stdin.** `cli/cli.py:463` calls
`get_prompt_from_stdin()` unconditionally, which does a blocking
`sys.stdin.read()` for any non-TTY stdin (so `echo "…" | vibe -p` works).
`_run_vibe` did not set `stdin`, so the child inherited the orchestrator's.

From a terminal, `isatty()` short-circuits and nothing happens. Under `nohup`,
`&`, a redirect, CI, or any supervising harness, stdin is a pipe that never
reaches EOF and **every agent hangs before its first LLM call** — proxy request
count 0, indistinguishable from a dead endpoint. Confirmed by stack-sampling a
hung agent (`_io_FileIO_readall_impl → read()`).

Now `stdin=asyncio.subprocess.DEVNULL`.

Faults 2 and 3 had never fired in production *because* fault 1 meant there was
never a second attempt and the operator always ran from a terminal. Fixing one
exposed the others.

## A fourth fault, found by the fixed harness

Worth calling out separately because it is the first thing the repaired loop
*discovered*, rather than something the audit found by reading.

**The memory block was prepended to the instruction, not appended.** Sec. 6.1
of the spec says the prompt is Block A (instruction, byte-identical for all
agents) → Block B (retrieved memory) → Block C (this attempt's error).
`_task_prompt` did `base = memory_context + "\n\n" + base`, making it **B, A,
C** — while the comment directly above it claimed otherwise.

Two costs, and the second is severe:

1. It destroys warm's shared prefix. Block A exists to be identical across all
   agents for the whole run so SGLang's RadixAttention can share it. A
   per-agent, per-attempt memory block in front of it means warm shares no
   prefix at all — a direct tax on the arm whose token count is the headline
   metric.
2. **It made warm agents answer the memory instead of doing the work.** An
   agent handed a page of "### Similar Past Tasks" before being told what to do
   reports on it. Measured on the 4-a-side run, same model, same everything
   else:

   | | attempts | assistant turns | tool calls | text-only turns |
   |---|---|---|---|---|
   | warm-1 | 3 | 6 | 4 | **2** |
   | warm-2 | 3 | 5 | 3 | **2** |
   | cold-2 | 1 | 8 | **8** | **0** |
   | cold-3 | 1 | 8 | **8** | **0** |

   Warm got ~2 productive turns per attempt against cold's 8, and its attempts
   finished in 65–142s against cold's 347–360s. Warm therefore racked up *more
   graded attempts* while doing roughly a quarter of the work per attempt —
   the same illusion as run 28's token_ratio, arriving by a new route.

Fixed to A → B → C, pinned by two tests: one asserting the order, one
asserting cold's whole prompt is a strict prefix of warm's (so the arms differ
in memory and nothing else).

## Also fixed

**Honesty of the measurement**

- **~10% of every run budget was spent before the agents started.** `deadline`
  was set at the top of `main_async`, so the 8 `render_config` calls, the MCP
  smoke tests, the memory warmups and the baseline pytest all came out of the
  agents' time. `RUN_START` was stamped at t=68.9s and every `--deadline-s 600`
  run reported a 533–546s wall-clock. The clock now starts with the agents, and
  `setup_s` is reported separately.
- **The warmup leaked the answer into the warm arm.** It stored *"migrating
  fastapi_mail config.py from pydantic BaseSettings to pydantic_settings for
  Pydantic v2"* under `user_identifier="warm"` on every run — the correct fix
  for the first file in the failure chain, in warm's scope and nowhere in
  cold's. Confirmed in the graph as warm-scope entities. Now a neutral string.
- **Gaming the oracle inflated `errors_cleared`.** The shim and gutted-code
  checks forced `passed = 0` and replaced `signature` with a synthetic
  sentence, which then entered `seen_signatures` — so a rejected attempt
  scored a "cleared error", on the metric used to compare the arms when
  neither converges. The checks still gate `success` (they must; see
  NOTES-hard-won.md), but no longer rewrite the tally. Rejections get their own
  `ATTEMPT_REJECTED` event, and rejected attempts contribute to neither
  progress measure.

**Vibe kept vanilla**

- **`PROXY_MAX_TOKENS` defaulted to 2048**, injecting a ceiling into every
  request Vibe sent — justified entirely by Qwen3's reasoning mode, i.e. the
  cheap stand-in. On Mistral Small 4 that truncates a turn mid-tool-call and
  yields malformed JSON, which is the exact symptom that previously led someone
  to hand-patch `get_tool_choice()`. Now off by default.

**neo4j-agent-memory used as shipped**

- **Dropped the `graphrag` MCP server** and its hand-written `RETRIEVAL_QUERY`.
  It duplicated `reasoning.search_steps()` / `get_trace_with_steps()`, which
  ship with the package — checked against the installed source. It also ran
  from `harness/neo4j-mcp-experiments/`, which was **never committed**, so on
  any clean clone `check_mcp_servers()` failed and the warm arm could not
  start at all. It contributed 40–70 calls per run to 40 runs that moved 0
  tests.
- **Stopped storing tool results as `:Message`.** Every stored message goes
  through entity extraction, and Vibe renders `read_file` with a line-number
  gutter, so **78 of 229 `:Entity` nodes** were names like `'100→'`, `'171→'`,
  `'0.17s'`. A third of the long-term graph was line numbers, and that is what
  `get_context(include_long_term=True)` served back as "what you remember".
  Tool output already reaches the graph as the owning step's `observation`.
- **`MEMORY_READ` is now actually emitted**, with `hits`, `sources` and
  `chars`. It was in the event schema from the start and never written to a
  single run log, so no run in this project's history could distinguish a warm
  agent that retrieved four useful traces from one that retrieved nothing.
- **The memory tools guide named a tool that no longer exists**
  (`graphrag_neo4j_vector`). It now names `memory_search` /
  `memory_get_context`, which is what the agent actually sees.
- **Retrieved traces are attributed in the prompt** (`- Learned by: warm-0`).
  The claim is "another agent already did this work"; an unattributed block of
  text does not say that.

**Dead and broken code**

- Deleted `scripts/run_m3.py` (ImportError on a function removed months ago),
  `scripts/validate_fixture.py` (`KeyError: 'files'`), and
  `scripts/verify_m2_sandboxes.py` (wrong kwarg + same KeyError). All three
  targeted the abandoned synthetic CFP fixture the build spec still describes.
- Deleted `ScopedMemory.prior_traces` (never called), the empty `ui/` and
  `queries/` directories.
- **Wired `install_cleanup_handlers`** — it had shipped since M2 and was never
  called, so Ctrl-C left every live sandbox running and billable. Then fixed
  the traceback that introduced: Daytona's SDK uses a thread pool, so an atexit
  sweep during interpreter shutdown dies with "cannot schedule new futures",
  printing a traceback *after* a clean summary. It now no-ops when nothing is
  live and never raises on the way out.
- Removed `FILE_CLAIMED` and `METRICS` from `EVENT_TYPES` (nothing emits them).
- `preflight()`'s `return 1` was **inside** the print loop, so only the first
  problem was ever shown.
- `agent_worker`'s bare `except Exception` retried instantly and forever. A
  missing `vibe` binary raises `FileNotFoundError`, which is an `OSError` and
  so not in `_HARNESS_BUGS` — that was a tight loop printing until the
  deadline. Now capped at 5 consecutive failures with exponential backoff.
- `check_containment` was annotated `-> list[str]` and returned a 2-tuple, and
  claimed to be a containment backstop while seeing only `edit`/`write_file` —
  Vibe also ships `bash`, `git_bash`, `experimental_bash`, all enabled, and
  agents use bash constantly. The claim is now scoped to what it checks.

**Reproducibility**

- `requirements-dev.txt` pinned a bare `neo4j-agent-memory`. The configured
  embedder needs `[openai]`; `ExtractionConfig(enable_llm_fallback=False)` is
  only defensible with `[gliner]` and `[spacy]`. A fresh clone installed a
  non-working orchestrator while the dev machine happened to have the extras.
  Now `neo4j-agent-memory[openai,gliner,spacy]` + `mcp` + `pytest-asyncio`.
- `runs/sample.jsonl` — the replay contract — described the abandoned fixture
  (`cfp/models/speaker.py`, `P1_VALIDATOR`, `FILE_CLAIMED`, `METRICS`). The
  test passed throughout because `load_events` only parses JSON. Regenerated
  from a real run, plus a test that every type in it is one the orchestrator
  emits. `runs/golden.jsonl` now exists.
- Three blocks of comment in `memory.py` claimed embeddings were local
  (`BAAI/bge-small-en-v1.5`, 384 dims, "no API key needed") while
  `EMBEDDING_MODEL` was `openai/text-embedding-3-small` (1536). Deleted rather
  than corrected.

**Tooling**

- `scripts/inspect_run.py` — prints the counts and **exits non-zero if
  `ATTEMPT_DONE` or `SANDBOX_CREATED` is 0**. The whole point is that a null
  run is indistinguishable from a real one in the printed summary.
- `tests/test_attempt_loop.py` — 13 tests pinning all three root causes,
  including one that demonstrates the stdin hang against a stand-in so it needs
  no GPU.

smaller in absolute terms (`vibe_agent.py` 1,703 → 1,635 with substantially
more code in it; `run.py` 1,065 → 1,005; `id_fix_proxy.py` 315 → 243).

The rule applied, which is worth keeping: **a run-number anecdote belongs in a
findings log, not above a `def`.** Keep the one-line *why* at the code and put
the measurement in `NOTES-hard-won.md`. The commentary was not wrong — most of

Still high, and deliberately: this codebase's failure modes are almost all
silent, and the comments that survived are the ones that stop someone
"simplifying" a guard back out.

## A fifth fault: attempts that did nothing were still graded

**Some attempts completed no assistant turn at all, burned ~135s, and were
graded anyway.**

Seen in the last 2-a-side run: `warm-1` did this on 3 of its 4 attempts,
`cold-0` on 2 of 4. The session directory contains the user prompt and **no
assistant message at all**; `vibe_exit=1` with no `<vibe_stop_event>`, so
`_ended_cleanly()` correctly refuses to resume and every attempt starts a fresh
session — which is why that run shows 4 session dirs per agent and only ~1 LLM
call per attempt.

Ruled out:

- *Not* the rejection-placement change. That run recorded **zero**
  `ATTEMPT_REJECTED`, so the notice was never added to any prompt.
- *Not* the endpoint. A direct probe through the same proxy immediately
  afterwards tool-called correctly in 12–32s and could still end a turn with
  text.
- *Not* agents bailing conversationally: **zero** text-only assistant turns in
  any session.
- *Not* `migrate_codebase` raising and being retried: attempt numbers run
  1,2,3,4 in the event log, so the loop iterated normally.

**Cause: endpoint saturation.** Re-run at `--swarm-size 1` with the new
instrumentation, both agents behaved perfectly:

```
warm-0 att=1 turns=9 resumed=False vibe_exit=1  stop='Turn limit of 8 reached'
cold-0 att=1 turns=9 resumed=False vibe_exit=1  stop='Turn limit of 8 reached'
```

`turns=9` is 1 user + 8 assistants — the full budget, limit fired, marker
present. So the loop is correct; under load Vibe's completions fail, it retries
with backoff, and it exits without ever finishing a turn. That is the "Server
disconnected" failure the README already lists, arriving one level down where
nothing could see it.

**Two things were done about it.**

*Make it visible.* `ATTEMPT_DONE` now carries `vibe_stop`, `turns_used` and
`resumed`. `vibe_output` was previously captured, matched against one regex and
discarded — so "hit the turn limit after 8 turns" and "died after 0 turns" were
indistinguishable in the event log while meaning opposite things. Same
blindness as the dead-MCP-server case, and the last place it was hiding.

*Stop grading it.* An attempt whose `_steps_used` did not advance is now
**aborted, not graded**: it emits `ATTEMPT_ABORTED`, does no memory replay,
spends no Daytona sandbox, does not inflate the attempt count, and backs off 5s
before retrying. Grading it was spending a sandbox to re-derive a verdict on a
byte-identical tree and writing a "no edit was made" trace that retrieval would
later surface as if it were knowledge.

`scripts/inspect_run.py` prints aborted attempts separately and flags any
graded attempt with `turns_used <= 1` as having done no work.

## What is still open

Ordered by what I would do next.

1. **Throughput is the binding constraint, not memory.** At ~36s/turn with 8
   agents on one A40, an agent gets ~17 turns per 600s no matter what memory
   does, and one dead end costs 6 of them. Neither arm converged in 900s.
   Either raise throughput (fewer agents per card, a second card, the real
   Mistral Small 4 on bigger hardware) or shorten the failure chain. **No
   amount of `min_trace_score` tuning fixes this.**
2. **`token_ratio` was 0.825–0.887 — warm cost more.** Expected and honest at
   this stage: warm carries the retrieved-memory block *and* 16 memory tool
   schemas on every request, and only breaks even once retrieval saves whole
   attempts. With the prompt order fixed, warm's attempts now run *longer*
   than cold's (median 430s vs 224s) rather than shorter, so the next ratio
   will be measuring real work on both sides for the first time. Worth
   measuring `--profile core` on the MCP server to cut the tool-schema tax.
3. **The shim is the model's first move and it keeps making it.** In the
   validation run **all nine** graded attempts were shims — `cold-1` on
   attempts 1, 2 *and* 3, `warm-1` on 1 and 2, with `pytest_passed` of 31 and
   32. I checked whether the feedback reached them rather than assuming: the
   `MIGRATION NOT COMPLETE` block *was* present in attempt 2's prompt, 85% of
   the way through 5,655 characters. Told plainly, ignored.

   Acted on once it was n=5 rather than n=1: the notice now goes at the **top**
   of the fed-back error instead of appended after the pytest output. The old
   placement was incidental (it is where `+=` puts things), and this is the
   most decision-relevant sentence in the prompt — the suite says 32 of 33 and
   the work is still rejected. It also now survives `_trim_error_for_prompt`
   by construction rather than by luck.

   **Whether that changes the behaviour is the open question.** If it does not,
   the answer is a better model, not a louder prompt — and definitely not
   naming the correct imports in Block A, which would make the demo a lie.

4. **Entity resolution is not merging.** Three `pydantic` nodes with
   contradictory type labels, `root_validator` as both `Object` and `Person`.
   The build spec asserts the resolver merges these. Check whether
   `enable_llm_fallback=False` suppresses the resolution pass before blaming
   `DeduplicationConfig`.
5. **No UI.** `ui/` was empty; the flash, the scoreboard and the closing Cypher
   do not exist. `MEMORY_READ` now carries the payload the flash needs
   (`hits`, `sources`), and `runs/golden.jsonl` exists to build against, but
   `EventBus` still never calls `broadcaster.serve()` so nothing can connect to
   a live run. That is M5 and it is a clean starting point now, not a blocker.
6. **Secrets sit where the agents can read them.** `_STRIPPED_ENV` removes
   `OPENAI_API_KEY` and `NEO4J_PASSWORD` from the agent's environment, and
   `render_config` then writes both in plaintext to
   `/tmp/msf-agents/{swarm}-{i}.vibe/config.toml` — a *sibling* of the agent's
   cwd, readable with one `cat`, by cold agents too. The "cold has zero path to
   Neo4j" claim holds only because no cold agent has read a file 40 characters
   away. Move the vibe homes out of `AGENT_ROOT`.
7. **Rotate the OpenAI key and the Aura password.** Both were in plaintext in
   `/tmp` and both appeared in audit output.
8. **The local suite takes ~70s on macOS** — `make_msgid()` → `getfqdn()` →
   5.01s DNS timeout × 14 tests. Costs nothing while imports are broken;
   becomes a real tax the moment an agent fixes them. Verify whether it
   reproduces in the Daytona container.
9. **`_collect_file_contents` uploads only `<package_path>`.** A new file the
   agent creates outside `fastapi_mail/` passes locally and is silently absent
   in the sandbox.
10. **The build spec is fiction.** `miss-slaytona-forje-spec.md` still describes
   a twelve-module CFP fixture with `P1…P6` pattern tags that was replaced by
   `fastapi-mail`. `README.md` is the accurate document. Either rewrite the
   spec or mark it historical.
